# Constraints: AI深蹲动作评估与训练反馈系统 V1.0

## 1. Ownership Constraints

- 本项目必须以独立开发为前提推进
- 不得直接复用权属不清的软件代码、组件、文案、图示、接口定义、数据库结构、截图模板
- 可以参考公开通用技术方案，但不能沿用带有公司产品指纹的表达和实现细节
- 若某模块被怀疑与历史公司项目过近，优先重写，不做“改一改继续用”

## 2. Product Constraints

- 产品只做“深蹲动作评估与训练反馈”，不扩展为综合康复平台
- V1.0 只支持单动作主线，不同时纳入亚当斯测试、ROM、语音问诊或多专项插件体系
- 不做后台工作台、筛查队列、机构管理、学校批量筛查

## 3. Claim Constraints

- 不得将产品描述为医疗诊断软件
- 不得输出“确诊”“诊断结果”“病理结论”“医学分型”等措辞
- 允许使用“动作评估”“风险提示”“训练反馈”“姿态表现”“建议”
- 若需要提及风险，只能表述为动作层面的代偿或控制风险，不得越界为临床结论

## 4. Architecture Constraints

- V1.0 保持单仓库前后端结构，不拆微服务
- 前端负责交互、采集流程、界面状态、可视化展示
- 后端负责数据存储、规则编排、报告摘要、配置默认值
- 业务逻辑放在 `service` 层，持久化放在 `repository` 层，避免路由层膨胀
- 接口统一采用 REST + JSON

## 5. Data Constraints

- API 字段统一使用 `snake_case`
- 历史记录必须保存时间戳、核心指标和评分结果
- 数据模型优先服务当前产品，不预埋大平台字段
- 若新增字段仅为“以后可能用”，默认不进入 V1.0

## 6. Design Constraints

- `frontend/src/shared/config/design-tokens.json` 是唯一设计 token 来源
- 页面颜色、间距、圆角、阴影、字号、层级必须优先映射 token
- 不允许在主样式中随意引入新的品牌色
- 不允许退化为默认蓝白 SaaS 风格
- 不允许用大量弱信息卡片把“深蹲”主题冲淡

## 7. Visual Direction Constraints

- 主品牌基调是 teal，不是 blue，不是 purple
- amber 只作为强调色和重点 CTA，不得大面积覆盖主界面
- neutral paper 负责页面基底和文档气质
- data blue 只用于图表、数据关系和信息强调，不应替代品牌主色
- 页面应该有训练/评估设备感，而不是医院 HIS 或企业管理后台感

## 8. Copyright Application Constraints

- 软件名称、文档名称、代码注释中的产品称谓需要保持一致
- 后续整理软著源程序时，不纳入第三方依赖、构建产物、缓存文件、自动生成文件
- V1.0 代码结构应能支持抽取核心源程序页，而不是依赖脚手架模板充数
- 说明文档中的功能边界必须与实际代码一致

## 9. Workflow Constraints

- 先改文档，再改边界类代码
- 如果发现实现与 `PRD.md`、`SPEC.md`、本约束文档冲突，先停下来修正文档或方案
- 任何会扩大产品边界的功能提案，必须先确认是否影响软著定位
- 本轮优先级是“边界正确”，不是“功能堆得快”
